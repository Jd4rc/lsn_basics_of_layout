# lsn_basics_of_layout

Учебный Django-проект: витрина магазина аквариумов, рыбок, растений и сопутствующего
оборудования. Есть вёрстка на шаблонах Django с наследованием от общего макета и
подшаблонами, каталог с постраничным выводом, страницы товаров и категорий, полный
CRUD товаров прямо на сайте (добавление, просмотр, редактирование, удаление) и форма
обратной связи. Все вьюхи написаны на классах — generic class-based views Django.
Данные — категории, товары и контактная информация магазина — хранятся в PostgreSQL,
все три модели также редактируются через админку.

## Стек

- Python 3.14
- Django 6.1
- Bootstrap 5 (подключён локально из `static/`)
- PostgreSQL (доступ через `psycopg`)
- Pillow — работа с изображениями для `ImageField`
- load-dotenv / python-dotenv — переменные окружения из `.env`
- Poetry — управление зависимостями

## Установка

```bash
git clone https://github.com/Jd4rc/lsn_basics_of_layout.git
cd lsn_basics_of_layout
poetry install
```

Создать файл `.env` в корне проекта с настройками подключения к PostgreSQL:

```
SECRET_KEY=django-insecure-...
DEBUG=True
DB_NAME=...
DB_USER=...
DB_PASSWORD=...
DB_HOST=localhost
DB_PORT=5432
```

Применить миграции, загрузить тестовые данные и запустить сервер:

```bash
poetry run python manage.py migrate
poetry run python manage.py load_fixture_catalog
poetry run python manage.py runserver
```

Если виртуальное окружение уже активировано, префикс `poetry run` можно опускать.

Загруженные фото товаров лежат в `media/`, а эта папка исключена из репозитория
(`.gitignore`). После свежего клонирования у товаров из фикстуры, для которых указано
фото, картинки не будут найдены — их нужно загрузить заново через админку или форму.
В режиме `DEBUG=True` файлы из `media/` раздаёт сам Django.

## Страницы

| URL | Метод | Имя маршрута | Вьюха | Шаблон |
|---|---|---|---|---|
| `/` | GET | `catalog:home` | `ProductListView` | `catalog/home.html` |
| `/contacts/` | GET, POST | `catalog:contacts` | `ContactFormView` | `catalog/contacts.html` |
| `/products/new/` | GET, POST | `catalog:product_create` | `ProductCreateView` | `catalog/product_form.html` |
| `/products/<int:pk>/` | GET | `catalog:product_detail` | `ProductDetailView` | `catalog/product_detail.html` |
| `/products/<int:pk>/edit/` | GET, POST | `catalog:product_update` | `ProductUpdateView` | `catalog/product_form.html` |
| `/products/<int:pk>/delete/` | GET, POST | `catalog:product_delete` | `ProductDeleteView` | `catalog/product_confirm_delete.html` |
| `/<slug>/` | GET | `catalog:category_detail` | `CategoryProductListView` | `catalog/category_detail.html` |
| `/admin/` | — | — | — | админка Django |

Маршруты приложения описаны в `catalog/urls.py` и подключены в `config/urls.py` через
`include('catalog.urls')`. Все адреса заканчиваются на `/`.

Маршрут категории `/<slug>/` стоит в `catalog/urls.py` последним: он подходит под
любое слово, поэтому все более частные адреса (`contacts/`, `products/...`) должны
проверяться раньше.

### Шаблоны

`templates/base.html` в корне проекта — общий макет: шапка, подвал, подключение
стилей и скриптов. Все страницы наследуются от него через `{% extends 'base.html' %}`
и переопределяют блоки `title` и `content`.

Повторяющиеся куски вынесены в подшаблоны и подключаются через `{% include %}`:

- `templates/includes/nav.html` — навигация: название магазина со ссылкой на главную, пункты
  всех категорий, «Добавить товар» и «Контакты». Подключается в `base.html`, поэтому
  есть на каждой странице.
- `templates/includes/pagination.html` — кнопки «Назад», номера страниц, «Вперёд».
  Ожидает в контексте переменную `page_obj`; если страница всего одна, ничего
  не выводит.
- `catalog/templates/catalog/includes/product_card.html` — карточка товара: фото,
  название со ссылкой на страницу товара, описание, обрезанное до 100 символов
  (`truncatechars:100`), и цена. Ожидает переменную `product`, используется на
  главной и на странице категории.

Список категорий для меню нужен в каждом шаблоне, поэтому его отдаёт контекст-процессор
`catalog.context_processors.menu_categories` (подключён в `TEMPLATES` в
`config/settings.py`) — вьюхам не приходится передавать его самим.

Шаблоны самого приложения лежат в `catalog/templates/catalog/` — вложенная папка
с именем приложения нужна, чтобы имена не конфликтовали с шаблонами других
приложений.

### Вьюхи

Все вьюхи в `catalog/views.py` — классы на основе generic CBV Django. В самих классах
почти только настройки: разбор запроса, формы, 404 и редиректы делает Django.

| Вьюха | Базовый класс | Что делает |
|---|---|---|
| `ProductListView` | `ListView` | главная: товары в продаже, по 6 на странице |
| `CategoryProductListView` | `ListView` | товары категории в продаже, по 6 на странице |
| `ProductDetailView` | `DetailView` | страница товара |
| `ProductCreateView` | `CreateView` | добавление товара |
| `ProductUpdateView` | `UpdateView` | редактирование товара |
| `ProductDeleteView` | `DeleteView` | удаление товара с подтверждением |
| `ContactFormView` | `FormView` + `SuccessMessageMixin` | форма обратной связи |

Шаблоны товара названы по умолчаниям Django (`product_detail.html`, `product_form.html`,
`product_confirm_delete.html`), поэтому `template_name` задан только у главной,
категории и контактов. Оба списка используют собственный миксин `NearestPageMixin`:
при неверном номере страницы он открывает ближайшую, а не отдаёт 404, как `ListView`
по умолчанию.

### Каталог

- **Главная** (`/`) — плитки категорий и блок «Сейчас в наличии»: товары с флагом
  «в продаже», по 6 на странице. Номер страницы передаётся в адресе: `/?page=2`.
  Неверный номер не вызывает ошибку: не число — открывается первая страница,
  слишком большой номер — последняя.
- **Категория** (`/<slug>/`) — описание категории и её товары в продаже, тоже по 6
  на странице с той же пагинацией. Для несуществующей категории — страница 404.
- **Товар** (`/products/<pk>/`) — фото, цена, описание целиком, категория, состояние,
  остаток, флаг «в продаже», даты добавления и обновления, кнопки «Редактировать»
  и «Удалить». Для несуществующего `pk` — страница 404.

Товары, снятые с продажи, не выводятся в списках, но их страница по прямой ссылке
открывается.

### Добавление и редактирование товара

Страницы `/products/new/` (`ProductCreateView`) и `/products/<pk>/edit/`
(`ProductUpdateView`), форма `catalog.forms.ProductForm` (`ModelForm` на модели
`Product`). Шаблон у обеих один — `product_form.html`: заголовок («Добавить товар» /
«Редактировать товар») и ссылка «Отмена» меняются в зависимости от того, новый
товар в форме или уже сохранённый.

- Поля: категория, название, описание, цена, остаток, состояние, фото, «в продаже».
- При редактировании форма открывается с текущими данными товара; фото можно
  заменить или убрать.
- Проверки на сервере:
  - название — не короче 3 символов (пробелы по краям обрезаются);
  - описание — обязательно, не короче 20 символов;
  - цена — больше нуля.
- Ошибки выводятся под соответствующими полями, введённые данные при этом
  сохраняются. Исключение — поле «Фото»: браузер не позволяет странице заполнить
  поле выбора файла, поэтому после ошибки файл нужно выбрать заново.
- Форма отправляется с `enctype="multipart/form-data"` — без этого файл не дойдёт
  до сервера. Загруженный файл в форму передаёт сам `CreateView` / `UpdateView`.
- После успешного сохранения — и нового товара, и отредактированного — редирект
  на страницу этого товара (схема Post/Redirect/Get), поэтому обновление страницы
  не отправляет форму повторно. Адрес берётся из `Product.get_absolute_url()`.

### Удаление товара

Страница `/products/<pk>/delete/` (`ProductDeleteView`). GET показывает подтверждение
с данными товара, удаляет товар только POST-запрос по кнопке «Удалить» (с CSRF-токеном),
после чего — редирект на главную. «Отмена» возвращает на страницу товара.

### Модели

- **`Category`** — категория товаров (`name`, `description`, `slug`), сортировка
  по названию.
- **`Product`** — товар: `ForeignKey` на `Category` (`on_delete=PROTECT`,
  `related_name='products'`), цена, остаток на складе, состояние (новый, б/у),
  флаг «в продаже» (`is_active`), фото, даты создания и обновления. Сортировка —
  сначала новые. `get_absolute_url()` возвращает адрес страницы товара.
- **`ContactInfo`** — контактные данные магазина (телефон, email, адрес, часы
  работы), заполняются через админку и выводятся на странице контактов.

У всех моделей есть `__str__` и класс `Meta` с `verbose_name` и `verbose_name_plural`.
Категорию, в которой есть товары, удалить нельзя (`PROTECT`): сначала нужно удалить
товары или перенести их в другую категорию.

### Тестовые данные и management-команды

`catalog_fixture.json` — ассортимент аквариумного магазина: 4 категории
(аквариумы, рыбки, растения, оборудование), 9 товаров и запись с контактами.

- `python manage.py load_fixture_catalog` — загружает фикстуру в базу.
- `python manage.py delete_data_in_db` — удаляет из базы все товары и категории
  (контакты не трогает).

Чтобы пересохранить фикстуру из текущей базы, используйте ключ `-o`:

```bash
poetry run python manage.py dumpdata catalog --indent 2 -o catalog_fixture.json
```

Перенаправление вывода через `>` в PowerShell сохраняет файл не в UTF-8, и русский
текст в фикстуре превращается в нечитаемые символы.

### Форма обратной связи

На странице контактов есть форма с полями «Имя», «Телефон» и «Сообщение» —
`catalog.forms.ContactForm`, обрабатывает её `ContactFormView`.

- Все поля обязательные, имя — до 100 символов, телефон — до 20. Ошибки выводятся
  по-русски под каждым полем, введённый текст при ошибке не пропадает.
- Отправленное сообщение выводится в консоль сервера, в базе оно не хранится.
- После успешной отправки — редирект обратно на `/contacts/` (Post/Redirect/Get),
  поэтому обновление страницы не отправляет сообщение повторно. Благодарность
  показывается один раз через `django.contrib.messages` (`SuccessMessageMixin`).

Это отдельно от блока контактной информации на той же странице — тот берётся
из модели `ContactInfo` и не связан с отправленной формой.

Форма защищена CSRF-токеном (`{% csrf_token %}` в шаблоне). При отправке запроса
в обход браузера — например, через Postman — нужно сначала выполнить GET, чтобы
получить cookie `csrftoken`, а затем передать её значение в поле
`csrfmiddlewaretoken` или в заголовке `X-CSRFToken`. Иначе Django вернёт
403 с текстом «CSRF verification failed».

### Оформление

Собственные стили — в `static/css/style.css`. Визуальная идея взята с киноафиши:
пыльно-розовый фон, крупные серифные заголовки, подписи узким гротеском в верхнем
регистре, чёрные рамки без скруглений и SVG-зерно поверх страницы. Фото в карточках
обрезаются до одинаковой высоты (`object-fit: cover`), длинные слова без пробелов
переносятся, а не вылезают за блок.

### Известные ограничения

- Входа на сайт нет: добавлять, редактировать и удалять товары может любой
  посетитель. Проект рассчитан на локальный запуск через `runserver`.
- Сообщения из формы обратной связи не сохраняются в базе.
- При удалении товара файл фото остаётся в `media/products/`.
- Категория со слагом `contacts` или `admin` будет недоступна: эти адреса раньше
  перехватят страница контактов и админка.
